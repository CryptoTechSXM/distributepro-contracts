## 2. Defects in the current contract

Ordered by what actually bites first.

### 2.1 🔴 The fee taper is dead code — everybody pays the maximum 2%

```solidity
uint256 minAmount = 10_000 ether;    // 10_000 * 10^18
uint256 maxAmount = 1_000_000 ether; // 1_000_000 * 10^18
```

`ether` is just `10^18`. The thresholds are therefore expressed in 18-decimal units, but
`calculateFee` is applied to **both ETH and any ERC-20, whatever its decimals**.

- **USDC / USDT are 6 decimals.** `10_000 ether` = 10^22 base units = **ten quadrillion USDC**.
  Every realistic stablecoin distribution lands in the `amount <= minAmount` branch → flat 2%.
- **For ETH**, 10,000 ETH is a multi-million-dollar batch. Also effectively always 2%.

So the entire linear taper — the most interesting part of the contract — never executes.
Any V3 fee curve must be **denominated per-token in that token's own decimals**, or priced off an
oracle, or expressed in basis points with no absolute thresholds at all.

### 2.2 🔴 `processToken` trusts a caller-supplied `total`

```solidity
function processToken(address token, address[] calldata recipients,
                      uint256[] calldata amounts, uint256 total) external {
```

`total` is a parameter; it is never checked against `sum(amounts)`. A caller can pass a small
`total` (so only a small `total + fee` is pulled in via `transferFrom`) while `amounts` sum to
much more — and the contract will then pay out `amounts` from **whatever token balance it happens
to hold**, i.e. other users' funds or accumulated dust. Fee is also under-charged.

**Fix: compute `total` in the contract from `amounts`. Never accept it as input.**

### 2.3 🔴 `.transfer()` will brick batches containing any contract wallet

```solidity
payable(recipients[i]).transfer(amounts[i]);
payable(feeRecipient).transfer(fee);
```

`.transfer()` forwards a 2,300-gas stipend. Any recipient that is a smart contract — a Gnosis Safe,
a multisig, most contract wallets, anything with a non-trivial `receive()` — will consume more than
that and revert. **One such address anywhere in the list and the whole distribution fails.**
For a batch payout tool aimed at businesses, this is the single most likely real-world failure.

Same hazard applies to `feeRecipient`: point it at a Safe and every distribution reverts.

**Fix: `(bool ok, ) = recipient.call{value: amount}(""); require(ok);`** — with reentrancy
protection, see 2.4.

### 2.4 🔴 No reentrancy guard

External calls inside a loop, to addresses the caller chooses. Mandatory once `.call` replaces
`.transfer` (2.3). Use OZ `ReentrancyGuard` and keep to checks-effects-interactions.

### 2.5 🟠 Real USDT on Ethereum mainnet will revert every time

```solidity
require(erc20.transfer(recipients[i], amounts[i]), "Distribution failed");
```

Tether on Ethereum mainnet does **not** return a bool from `transfer`/`transferFrom`, in violation
of ERC-20. Solidity's ABI decoder reverts when it gets no return data for a `bool`.

Note the trap this repo is in: `MockUSDT.sol` is a plain OpenZeppelin `ERC20`, which *does* return
a bool — **so the mock cannot reproduce the bug.** Tests against it will pass and mainnet will fail.

**Fix: OZ `SafeERC20` (`safeTransfer` / `safeTransferFrom`), and add a non-compliant mock that
returns nothing, so the test suite actually covers this case.**

### 2.6 🟠 ETH overpayment is permanently lost

`require(msg.value >= total + fee)` accepts more than needed and never refunds the difference.
There is no `withdraw`, no sweep, no `receive()`. Anything overpaid is **locked in the contract
forever**. Add either an exact-amount requirement or an explicit refund of `msg.value - total - fee`,
plus an owner rescue function for stranded ETH and tokens.

### 2.7 🟠 Fee-on-transfer and rebasing tokens silently under-deliver

`transferFrom(msg.sender, address(this), total + fee)` may deliver less than requested for tokens
that tax transfers. The contract then tries to pay out the full `amounts` and either reverts
mid-loop or dips into other balances. **Fix: measure `balanceOf(address(this))` before and after
and work from the delta**, or explicitly reject fee-on-transfer tokens.

### 2.8 🟡 Unbounded arrays — gas-limit DoS

No cap on `recipients.length`. A large CSV produces a transaction that cannot fit in a block and
fails after the user has paid gas. Enforce a `MAX_RECIPIENTS` and have the frontend chunk beyond it.
Related, for CryptoNova work: the measured Base Sepolia per-tx gas ceiling is 16,777,216 (2^24).

### 2.9 🟡 No pause, no zero-address / duplicate-recipient checks

No emergency stop. `recipients[i]` is never checked against `address(0)` (burns funds) and
duplicates are not detected (silent double-pay — a plausible CSV mistake).

### 2.10 🟡 OpenZeppelin v5 will break the constructor

`Ownable()` with no argument is v4 syntax. Pinned at `^4.9.6` so it compiles today, but OZ v5
requires `Ownable(initialOwner)`. Pin deliberately or migrate deliberately — don't let a `^` range
decide.

## 4. Decisions needed before V3 is written

These are the owner's calls, not Claude's — they are product and economics, not code.

1. **Percentages or absolute amounts?** V1/V2 took basis-point percentages; V2.1 takes absolute
   amounts. Percentages suit "split this pot"; absolute amounts suit payroll. Supporting both is
   possible but doubles the surface. The website currently describes the **percentage** model
   ("percentages must total 100%, then add 2%").
2. **What is the fee, really?** The taper (2% → 0.5%) is a good idea that has never actually run.
   Options: flat basis-point fee (simplest, honest); per-token tiers in that token's own decimals;
   or a fee in a stable unit via an oracle (most complex, adds an oracle dependency).
3. **Who can change the fee, and is there a ceiling?** V2.0 allowed up to 100% — that must never
   ship. A hard cap in code (say 3%) plus a timelock on increases is what makes the contract
   trustworthy to people who are not you.
4. **Which chains actually matter at launch?** Seven configured, zero deployed. Pick one or two.
5. **Native ETH and ERC-20 in one contract, or split?** Combining them is where most of the
   complexity and most of the defects above come from.
6. **Audit?** Nothing is live, so now is the cheap moment to decide whether this ever holds real
   third-party money and therefore whether it needs external review.

## 5. Recommended shape for V3

Opinionated starting point, to be argued with:

- Solidity `^0.8.24`, OZ v5 pinned exactly (not `^`).
- `SafeERC20` throughout; `.call` for native; `ReentrancyGuard`; `Pausable`.
- `total` always computed on-chain from `amounts`. Never a parameter.
- Fee as **basis points with a hard-coded maximum**, settable by owner below that cap. Drop the
  amount-based taper until there is a decimals-correct way to express it.
- Balance-delta accounting on token pulls, so fee-on-transfer tokens can't desync the books.
- Explicit refund of native overpayment, plus owner rescue for stranded assets.
- `MAX_RECIPIENTS` cap, with chunking in the frontend.
- Reject `address(0)`; decide explicitly whether duplicates revert or are allowed.
- A real test suite: happy path, contract-wallet recipient, non-compliant USDT mock,
  fee-on-transfer mock, overpayment refund, reentrancy attempt, array-mismatch, oversized batch.
- One `--network` deploy per invocation; delete `deploy-multichain.js` or install the plugin.
- Delete the Lock.* template files.

# 7. OWNER DECISIONS — LOCKED 2026-09-11

Answers to §4, given by CryptoTech. These are settled. Build to them.

## 7.1 Model: PERCENTAGES

Basis points that must sum to 10000. Reverts back to the V1/V2 model and away from V2.1's absolute
amounts. This also matches what the website already says.

**Consequence — this single decision kills defect §2.1 outright.** The dead fee taper existed only
because thresholds were expressed in absolute `10^18` units and then applied to 6-decimal tokens.
A basis-point fee is decimals-agnostic by construction. There is now no absolute-unit constant
anywhere in the fee path, so the bug cannot recur.

**⛔ STRUCTURAL RULE for V3:** no value in shared code is ever expressed in absolute token units.
Basis points only. Absolute amounts exist solely as the caller's total payout and the derived
per-recipient figures.

## 7.2 Fee: 2% floor, 5% hard cap, partner revenue share

The owner's schedule, as given:

| Total fee | Crypto Counsel | Partner keeps |
|---|---|---|
| 2.0% | 2.00% | 0.00% |
| 2.5% | 2.00% | 0.50% |
| 3.0% | 2.00% | 1.00% |
| 3.5% | 2.00% | 1.50% |
| 4.0% | 2.00% | 2.00% |
| 4.5% | 2.25% | 2.25% |
| 5.0% | 2.50% | 2.50% |

**This table is a closed-form rule, not a lookup table.** Every row satisfies:

```
ccBps      = max(200, totalBps / 2)
partnerBps = totalBps - ccBps
```

Check: 200→max(200,100)=200, partner 0 ✓ · 300→200, partner 100 ✓ · 400→max(200,200)=200,
partner 200 ✓ · 450→max(200,225)=225, partner 225 ✓ · 500→250, partner 250 ✓.

So V3 implements two lines of arithmetic, not a seven-row table, and any total in the range works —
not only the 0.5% steps. The frontend can still offer the steps as presets.

**Hard bounds in code: `200 <= totalBps <= 500`.** 200 is the floor (Crypto Counsel's minimum),
500 is the ceiling. The V2.0 "owner may set up to 100%" behaviour must never ship.

**Measured property of this schedule, worth stating: it is incentive-safe.** Crypto Counsel's take
never drops below 2%, and rises with the total. A caller who registered themselves as their own
partner and chose 5% would pay Crypto Counsel 2.5% instead of 2% — self-dealing costs them money.
There is no configuration in which naming a partner reduces Crypto Counsel's revenue.

**Open sub-question (small, product not code):** who *selects* the total for a given distribution —
an owner-controlled partner registry (`partner address -> totalBps`), or a caller-supplied
parameter? Recommendation: **owner-controlled registry.** Simplest, no abuse surface, and a partner
rate is a commercial agreement, not a per-transaction choice. Unregistered callers get the 200bps
floor with no partner.

## 7.3 ⛔ NEVER HOLD THIRD-PARTY FUNDS — pure pass-through

Owner's words: *"Never hold 3rd party funds pure blockchain splits."*

This is the strongest constraint in the design and it rewrites several audit items:

- **Contract balance at rest is ZERO.** Every wei and every token unit that enters in a transaction
  leaves in that same transaction. Nothing accrues, nothing is claimed later.
- **The fee is paid out inside the same call** — to Crypto Counsel and to the partner. No fee
  accrual, no `withdrawFees()`.
- **§2.6 (locked ETH overpayment) becomes non-negotiable.** Either require exact `msg.value`, or
  refund the remainder in the same transaction. Recommendation: **require exact** — it is one
  `require`, it cannot silently strand funds, and the frontend computes the number anyway.
- **§2.2 (caller-supplied `total`) is not merely a bug, it is the attack this constraint forbids.**
  With a zero balance at rest there is nothing to steal, which is defence in depth — but `total`
  must still be computed on-chain from the percentages. Never a parameter.
- **The owner rescue function changes meaning.** It is no longer for sweeping user funds; it exists
  only for assets sent to the contract by mistake, outside a distribution. Keep it, scope it that
  way, and say so in the code comment.

**New problem this constraint creates: DUST.** Percentages plus integer division leave a remainder.
In a contract that holds nothing, the remainder cannot be left behind — accumulated dust *is*
holding funds. V3 must assign it deterministically in the same transaction. Recommendation: **the
remainder goes to the last recipient**, documented in the code and shown in the frontend summary.
Decide and write it down; do not let it emerge from rounding by accident.

# 8. ARCHITECTURE — one contract or split?

Owner asked for pros and cons. Recorded here with the recommendation.

## 8.1 Split (DistributeNative + DistributeToken)

**For:** each contract does exactly one thing; the native path never touches decimals and the token
path never touches `msg.value`; smaller bytecode each; deploy only what a chain needs; the class of
bug that killed V2.1 becomes structurally impossible.

**Against:** two addresses per chain, multiplied by every chain — more to deploy, verify, track and
keep in sync; the fee schedule, partner registry, percentage validation and recipient checks are
duplicated or need a shared base, and duplicated logic drifts; two pause switches and two owners to
keep aligned; the frontend has to choose.

## 8.2 One contract, two entry points

**For:** one address per chain — which matters more with every chain added, and §7.4 adds chains;
one fee configuration, one partner registry, one pause switch, one owner, with no possibility of
the two halves drifting apart; shared logic written and audited once; a pass-through splitter is
small, so EIP-170's 24KB limit is not a constraint.

**Against:** native and ERC-20 have genuinely different failure modes and one contract invites
conflating them; `msg.value` must be explicitly required to be zero on the token path; more
branches to reason about.

## 8.3 ▶ RECOMMENDATION: ONE CONTRACT

`distributeNative(...)` and `distributeToken(...)` as separate external entry points, with
percentage validation, the fee schedule, the partner split and recipient checks in internal
functions used by both.

**The reasoning, and it is specific:** the strongest argument for splitting is that V2.1's worst bug
came from native and token sharing code. That is not actually what happened. V2.1's bug came from a
fee threshold expressed in **absolute units** being applied to tokens of different decimals. The
percentage decision in §7.1 removes absolute units from the fee path entirely. The argument for
splitting therefore evaporates with decision 7.1 — and the cost of splitting (N chains × 2
addresses, duplicated fee and partner logic that can drift) is paid on every chain, forever.

Guarded by the §7.1 structural rule — basis points only in shared code — one contract is the right
shape.

## 11.1 Two design points settled while writing it

**Rounding uses ceil, not floor.** `houseBps = max(200, ceil(totalBps/2))`. Only matters for an odd
bps value: at 401, floor would give the house 200 and the partner 201 — the partner out-earning
Crypto Counsel above the 4% line, which inverts the intent. ceil holds `house >= partner`. Both
agree on every row of the owner's table, so this changes nothing he specified.

**The HOUSE absorbs the rounding remainder, not the partner.** `partnerFee` is computed from bps
and `houseFee` is derived as `totalFee - partnerFee`. Two independent percentage calculations would
each round down and strand a wei or two on every distribution — under §7.3 that is a correctness
bug, not a rounding detail. Deriving one side as the remainder makes `houseFee + partnerFee ==
totalFee` exact by construction, and taking the remainder on the house side makes `houseFee >=
partnerFee` provably always true rather than true-in-practice.

Verified in Python across **3,913** rate/payout combinations before a line of Solidity was written:
zero dust, zero inversions, all seven owner rows exact.

## 17.1 ▶ THE DESIGN CONSEQUENCE: a static cap cannot do this job

At 50% of an 8,000,000 block:

| recipients | all-new | all-existing |
|---|---|---|
| 109 | 3,926,289 fits | 1,030,159 fits |
| **159** (his real batch) | 5,727,339 fits | **1,502,709 fits** |
| 250 | 9,005,250 **over the whole block** | 2,362,750 fits |
| 423 | 15,236,883 **over the whole block** | 3,997,773 fits |

- A cap safe for all-new addresses is **111**.
- His current, working, 159-recipient batches need **159**.

**No single number is both safe and permissive.** A cap of 109 would reject batches that demonstrably
succeed on-chain today — a regression from V1. A cap of 423 would let an all-new batch fail after
the gas was paid.

**So `maxRecipients` stops being the precision instrument and becomes a cheap backstop against
absurd input** — it reverts in `_validate()` before a single transfer, so it costs almost nothing.
The real decision moves to the frontend, which must **chunk by ESTIMATED GAS, not by count**:
call `eth_estimateGas` on the candidate batch (it knows which addresses already exist, because the
chain does) and split until each chunk sits under ~50% of the block limit. That adapts per chain,
per batch and per payee list with no redeploy.

**Recommended settings:** `maxRecipients` = **250** on BTC20 — comfortably above his real 159 usage,
far below anything absurd — with gas-estimated chunking in the frontend as the actual safety
mechanism. `MAX_RECIPIENTS_LIMIT` (500) stays the hard ceiling.

## 17.2 [owner, 2026-09-11] Chunking is confirmed product policy

His words: *"we cannot tell someone with 500 transactions or 5000 transactions we are not capable
of doing the transaction for them."*

`maxRecipients` is a **per-transaction batch size, never a product limit**. A 5,000-name CSV is
`ceil(5000 / chunk)` transactions with a progress bar, and the answer is always yes.

## 20.5 ⛔⛔ A GUARD THAT DID NOT GUARD — `CONFIRM=yes` survives the whole PowerShell window

**This is not hypothetical. It happened on 2026-09-12 and it spent the owner's money.**

`measure_token_overshoot.js` was handed over as a DRY RUN that "spends nothing". On its very first
invocation it sent **five transactions** and moved real USDT. Nothing was lost — the payout
returned, the arms were valid, the numbers in §19.7 are the result — but **the sentence on the
screen was false, and it was false because of a defect in the instrument, not an accident.**

- ⛔ **THE CAUSE, read off the transcript rather than guessed.** In PowerShell `$env:CONFIRM="yes"`
  is a **SESSION** variable: it lives for the life of the **WINDOW**, not the command. An earlier
  token run in that same window had set `CONFIRM`, `TOKEN`, `PAYOUT`, `RECIPIENTS` and `SHARES`.
  All of them were still set. The new script read `CONFIRM`, found `"yes"`, and armed itself.
- ⛔⛔ **AND IT WAS NEVER ABOUT ONE SCRIPT. FIVE scripts in this repo gated on the same generic
  word**, so in that window not one of them had a dry run any more:

  | script | what `CONFIRM=yes` did |
  |---|---|
  | `deploy_v3.js` | **deploy a NEW contract to BTC20 mainnet** and rename the deployment record |
  | `set_partner.js` | write a partner rate on-chain |
  | `testrun_v3.js` | send native coin |
  | `testrun_token_v3.js` | send ERC-20 (`APPROVE=yes` likewise) |
  | `measure_token_overshoot.js` | the run above |

  ▶ **`deploy_v3.js` is the one that mattered.** Its mainnet gate is the only thing between a
  stray `npx hardhat run` and a new live contract, and it was open.
- ✅ **THE FIX, in `scripts/utils/session_env.js` (new):** every script now demands its **OWN
  confirmation phrase** — `CONFIRM="deploy-v3"`, `"set-partner"`, `"testrun-native"`,
  `"testrun-token"` / `APPROVE="approve-token"`, `"measure-overshoot"`. A stale generic `"yes"`
  matches nothing, so the script falls back to its dry run, **which is the direction a stale
  variable must always fail in**. A phrase left over from a *different* script does not arm this
  one either. When it refuses it **says so out loud** — a guard that refuses in silence teaches
  the reader that the variable is broken, and the next thing they try is worse.
- ✅ **AND THE SECOND HALF, which matters as much: `reportEnv()` PRINTS every recognised variable
  it can see, before any work.** That run also silently inherited `RECIPIENTS`, `SHARES`, `TOKEN`
  and `PAYOUT`. Those did no harm **by luck, not by design** — they happened to be the §19.6
  recipients, which is the only reason arm A was comparable to §19.6 at all. ▶ **Input that
  arrives invisibly is the same defect family as §20.4: a figure shown without its basis.**
- ✅ **PROVEN BY EXECUTION, not by reading the source** (the §19.6 lesson): the guard was driven
  through five cases in node — `"yes"`, the correct phrase, unset, empty, and *another script's*
  phrase. Only the correct phrase arms.
- ▶ **THE LESSON: a gate is only as good as the freshness of the thing that opens it.** Any
  confirmation read from ambient state — an env var, a config file, a saved flag — can be stale,
  and a stale confirmation is indistinguishable from a deliberate one unless the value itself is
  specific to this run.
